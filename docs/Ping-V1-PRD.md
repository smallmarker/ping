## 2. 产品背景

Ping 是首个独立产品实践项目，目标是在可控成本内完成从想法、开发、上线、数据验证到迭代的完整闭环，并沉淀微信小程序、云开发、AI 接入和数据分析经验。

用户在微信聊天、群通知和日常沟通中常收到带时间的临时事项，但将一条消息变成可靠提醒的步骤过多：复制、打开日历或待办、填写标题、选择日期时间、设置通知。结果通常是“看到了但忘了设”。Ping 将这一动作压缩为：**输入/粘贴一句话 → AI 预填 → 用户确认 → 到点提醒**。

V1 必须克制：首版优先验证“用户是否愿意用自然语言快速创建提醒，以及通知是否能促成再次使用”，而非构建任务管理体系。复杂 Todo、项目、标签、协作和知识库会显著增加信息架构、数据模型与验证周期，却不直接缩短核心路径。Ping 的核心价值是：把“怕忘”快速转化为“已经设好提醒”。

## 3. 产品目标

| 类别 | 目标 |
| --- | --- |
| 用户目标 | 用户可在 10 秒内把一句自然语言转成一条已保存的提醒；解析不准时可无障碍手动修正。 |
| 产品目标 | 验证文字输入/剪贴板创建提醒的需求、解析质量和订阅消息触达价值。 |
| 开发目标 | 基于微信原生小程序 + CloudBase，以最少服务组件完成稳定闭环，避免独立服务器和复杂后台。 |
| 验证目标 | 30 天左右上线；获取 50 位真实陌生用户、200 条提醒、10 条有效反馈，并完成一次基于反馈的迭代。 |

## 4. 产品定位

**一句话定位：** Ping 是一个把自然语言快速变成到点提醒的轻量微信小程序。

**非定位：** 不管理长期目标、项目进度、子任务或知识内容；不提供 AI 对话、协作、社交和复杂标签。

| 对比对象 | 主要区别 |
| --- | --- |
| 传统 Todo | Todo 强调持续规划与任务管理；Ping 只优化临时事项的快速建提醒。 |
| 日历 | 日历重日程查看和时间排布；Ping 先理解一句话、后完成提醒。 |
| 备忘录 | 备忘录重保存内容；Ping 以可靠的未来通知为最终结果。 |

V1 的价值主张：**不用整理，一句话也能设好提醒。**

## 5. 核心用户与使用场景

| 用户 | 特征 | 典型场景 | 核心需求 |
| --- | --- | --- | --- |
| 聊天消息接收者 | 高频使用微信，临时约定和通知分散在聊天中 | 复制“周六 3 点环球中心见，带身份证” | 粘贴后少操作地生成提醒 |
| 容易忘事者 | 有记住意愿但不会立即打开复杂工具 | 看到快递、缴费、就医等临时事项 | 快速得到可靠提醒与可见确认 |
| 抗拒复杂工具者 | 不愿维护列表、标签和项目 | 仅偶发地设一个提醒 | 无学习成本、无需规划 |
| 临时提醒需求者 | 时间信息明确，时效高 | “明天下午 3 点去医院” | 准确识别时间并准时通知 |

## 6. 核心场景

| 场景 | 用户目标与前置条件 | 操作路径 | 成功结果 | 失败/异常处理 |
| --- | --- | --- | --- |
| 复制微信文本 | 已在微信复制一段含事项/时间的文字；进入 Ping | 首页识别剪贴板 → 用户同意使用 → 解析 → 确认并保存 | 生成一条带具体提醒时间的事项 | 用户拒绝则不读取、不上传；剪贴板无时间或解析失败时进入手动填写确认页 |
| 主动输入 | 已打开首页 | 输入一句话 → 点击“Ping 一下” → 解析 → 确认保存 | 在列表出现待提醒事项 | 网络/AI 失败时保留输入并提供“手动填写” |
| AI 错误后编辑 | 已到确认页或详情页 | 修改标题、日期、时间、地点、备注、提前提醒 → 保存 | 保存以用户编辑内容为准 | 必填项或时间非法时就地提示并禁止提交 |
| 到点通知 | 已保存事项；用户已授权对应订阅消息 | 到达 `notifyAt` → 云端扫描 → 发送订阅消息 → 用户点击消息回到详情 | 用户收到提醒并可查看、完成或删除 | 未授权/额度/平台限制时，列表仍显示；不承诺后台必达，见 11.8 |
| 查看提醒 | 已有提醒 | 首页查看今天/未来/已完成 → 点击卡片 | 找到事项并进入详情 | 无数据展示引导创建；加载失败支持重试 |

## 7. V1 范围

| 分层 | 功能 | 原因 |
| --- | --- | --- |
| 必须做 | 文本输入、用户确认后的剪贴板使用、AI 解析、确认/手动编辑、创建/列表/详情/完成/删除、订阅消息接入、基础埋点与反馈 | 构成“文字到提醒”的最小可验证闭环 |
| 可以做但不优先 | 语音转文字、图片 OCR 输入 | 可拓宽入口，但不影响文字核心闭环；仅在 P0 稳定后投入 |
| 明确不做 | GTD、四象限、项目/看板/子任务、复杂标签、知识库、AI 聊天/RAG、社区好友协作、积分会员、复杂后台、重复提醒、日历同步 | 不直接降低创建提醒的成本，且会延长首版上线周期 |

## 8. 核心用户流程

### 8.1 手动输入创建

进入首页 → 输入提醒文本 → 点击“Ping 一下” → 调用 AI 解析 → 进入提醒确认页 → 用户确认/修改 → 请求订阅消息授权 → 保存提醒 → 到达提醒时间后尝试发送订阅消息。

### 8.2 剪贴板创建

在微信复制文本 → 打开 Ping → 本地读取剪贴板并仅显示提示卡片 → 用户点击“使用此内容” → 调用 AI 解析 → 进入确认页 → 确认并保存。用户关闭卡片或拒绝时不上传文本。

### 8.3 编辑提醒

首页/详情页 → 点击“编辑” → 修改标题/时间/地点/备注/提前提醒 → 校验 → 保存 → 更新详情、分组和下一次通知任务状态。

### 8.4 完成与删除

详情或列表操作 → 标记完成/删除二次确认 → 云端更新状态 → 列表即时移入“已完成”/移除 → 取消后续发送资格。删除后默认不在前台展示。

## 9. 页面结构

```text
首页（创建入口、今天/未来列表、已完成入口）
├─ 提醒确认页（AI 结果校正与保存）
├─ 提醒详情页（查看、编辑、完成、删除）
└─ 我的页（统计、反馈、协议、关于）
```

首页负责创建与发现；确认页负责让用户对 AI 结果负责；详情页负责单条后续操作；我的页承载必要说明、反馈与轻量统计。

## 10. 页面详细需求

### 10.1 首页

| 项目 | 需求 |
| --- | --- |
| 目标/入口 | 小程序默认页；快速创建并查看未完成提醒。 |
| 元素 | 品牌“Ping / 怕忘？Ping 一下”、多行文本框、“Ping 一下”按钮、可关闭剪贴板提示卡、今天/未来分组、已完成入口。 |
| 输入框 | placeholder：`例如：明天下午 3 点提醒我去拿快递`；最大 500 字。0 字时按钮置灰；超限禁止继续输入并显示字数。 |
| 创建交互 | 点击后按钮禁用并显示“正在理解…”，输入保持原值；解析成功跳确认页，失败显示“没能理解这句话，可手动填写”，提供重试和手动填写。 |
| 剪贴板 | 页面 `onShow` 时读取；仅文本、长度 1–500、与上次忽略内容不同才显示卡片前 80 字预览。卡片须明确“使用后才会发送给 AI 解析”；“使用此内容”才将完整文本传入解析；“暂不使用”本次会话不再提示该 hash。 |
| 列表 | 过去日期：本地日历日早于今天且 `pending`，按真实日期显示“已过期”；今天：本地日历日内且 `pending`；未来：明日及以后 `pending`。组内按 `createdAt` 倒序，日期组按组内最新创建记录排序，最新新增的提醒优先显示。点击进入详情。已完成只展示入口和数量。 |
| 状态 | 首次空状态提示“把一句想记住的话 Ping 一下”；列表 skeleton；加载失败显示重试。 |

### 10.2 提醒确认页

| 项目 | 需求 |
| --- | --- |
| 入口/目标 | 仅由解析完成或手动填写进入；将可编辑草稿保存为有效提醒。 |
| 字段 | 标题（必填，1–60 字）、日期（必填）、时间（必填）、地点（选填，0–100 字）、备注（选填，0–300 字）、提醒时间（必填，默认准时提醒）、原始文本（只读，可折叠）。 |
| 编辑 | 日期/时间用小程序 picker；提醒时间使用“准时/提前 5/15/30/60 分钟”单选，计算 `notifyAt=remindAt-offset`。标题等文本字段可直接改。 |
| 时间缺失 | 不自动猜测后保存。日期或时间缺失时对应字段显示“请选择”，顶部提示“补全时间后即可设提醒”，确认按钮不可点击。 |
| AI 置信度 | V1 不展示具体分数，避免制造虚假的精确感；当 `<0.60`、缺时间或解析有歧义时显示“建议检查时间和事项”。具体数值仅保存用于分析。 |
| 保存/授权 | 点击“确认提醒”先执行本地校验；在微信允许的订阅消息授权窗口内请求模板授权，再创建。授权成功记 `authorized`；拒绝/关闭仍允许保存，记 `denied` 并说明“提醒将只保存在 Ping 中”。 |
| 状态 | 保存中按钮禁用；成功 toast 后跳详情（或返回首页）；失败保留编辑内容并可重试。 |

### 10.3 提醒详情页

展示标题、提醒日期时间、提前提醒、地点、备注、来源、状态；`pending` 显示“编辑”“标记完成”“删除”，`completed` 显示完成时间和“恢复为待完成”（**待确认：V1 是否开放恢复；默认不开放**）及删除。删除需二次确认。操作成功后刷新首页数据；返回默认回首页。

### 10.4 我的页

V1 必须：累计创建数、已完成数、反馈建议入口、隐私政策、用户协议、关于 Ping、版本号。反馈可简化为跳转客服/表单或复制反馈渠道（具体渠道待确认）；无需独立复杂后台。统计加载失败显示 `--`，不影响其他入口。

## 11. 功能需求

### 11.1 自然语言解析

输入为经用户提交的 1–500 字文本、客户端当前时间和 `Asia/Shanghai` 时区；输出结构化草稿。解析成功并不等于可保存：仅当标题、日期、时间完整且时间有效，确认页才可提交。无法识别时保留原文并创建空白可编辑草稿；不得直接创建提醒。

### 11.2 剪贴板识别

仅在用户进入首页时本地检测文本。不得自动调用 AI、不得持久保存未经确认内容、不得向服务端上传。内容为空、超过 500 字、纯链接/验证码/无可读文字时不提示；“看起来不像提醒”可提示“仍可使用并手动调整”，不应强拦截。

### 11.3 提醒创建

创建前校验标题、`remindAt`、`remindOffsetMinutes`，并要求 `notifyAt` 不早于当前时刻；服务端再次校验且以 openid 归属。成功返回 `_id` 并 toast“提醒已设好”；失败不清空草稿。

### 11.4 提醒列表

仅查询当前用户、未删除数据。首页查询先按 `createdAt DESC` 再取分页记录，按本地日历日分组；组内保持创建时间倒序，日期组按组内最新创建记录排序。过去日期使用真实日期标题并标注“已过期”，不得混入今天。已完成按 `completedAt DESC`。已过期而未完成的事项不自动完成；详情可重新设定时间、标记完成或删除。

### 11.5 编辑提醒

可编辑标题、时间、地点、备注、提前分钟；不可编辑来源和创建时间。修改时间/提前分钟后，重置 `notifyStatus`：若用户曾授权且平台授权凭证仍可用，置 `authorized`，否则 `pending/denied`，并按当前会话规则再次请求授权；已完成事项默认不可编辑（待确认）。

### 11.6 删除提醒

建议 V1 采用软删除：`status=deleted`、写入 `deletedAt`，前台和常规查询排除；保留 30 天用于故障排查与用户数据删除请求处理，后由定时任务物理清除（待确认）。删除时 `sendReminder` 必须过滤 `deleted`。

### 11.7 完成提醒

`pending → completed`，写入 `completedAt`；完成后不再发送通知。V1 不支持批量完成、不自动完成、不提供任务进度。

### 11.8 到点提醒

创建/编辑时在用户主动点击保存的界面请求一次订阅消息授权，并保存可发送所需的模板/授权信息（实现以微信订阅消息当前规则为准）。`sendReminder` 定时扫描 `pending`、`notifyStatus=authorized`、`notifyAt <= now` 的事项，发送后记录结果，须幂等。

**限制与降级：** 小程序订阅消息的模板、授权次数、可发送窗口及服务端调用规则受微信平台约束，不能将其视为永久后台闹钟。若未授权、凭证失效、模板不可用或发送失败，提醒仍保存在列表，显示“未能发送通知”；下次用户主动创建时可再次引导授权。**待确认：** 上线前由开发按目标模板和当前微信后台能力完成一次真机验证，并据此确定 `sendReminder` 的最终触发方式。

## 12. AI 解析需求

### 12.1 输入

```json
{
  "text": "周六下午3点环球中心见，记得带身份证",
  "currentTime": "2026-09-03T10:20:00+08:00",
  "timezone": "Asia/Shanghai",
  "locale": "zh-CN",
  "context": { "weekStartsOn": 1 }
}
```

不发送 openid、昵称、聊天对象或完整剪贴板历史。`context` V1 可为空。

### 12.2 输出 JSON Schema（逻辑约束）

```json
{
  "title": "和老王见面",
  "remindAt": "2026-09-05T15:00:00+08:00",
  "location": "环球中心",
  "note": "记得带身份证",
  "confidence": 0.86,
  "missingFields": [],
  "needUserConfirm": true,
  "rawTimeText": "周六下午3点",
  "timePrecision": "minute",
  "parseWarnings": [],
  "modelVersion": "provider/model-version"
}
```

约束：`title` 最多 60 字；`confidence` 为 0–1；`missingFields` 仅允许 `title/date/time`；`timePrecision` 为 `date|hour|minute|unknown`；AI 必须只返回 JSON。云函数必须校验 JSON、类型、时区和日期，不能信任模型输出。

### 12.3 时间解析规则

| 表达 | 规则 |
| --- | --- |
| 等会三点55、三点半、三点一刻 | 未指定日期和时段的口语 1–12 点，从今天/明天的上午、下午候选中选择最近的未来时间，并提示确认。例如 15:50 输入“三点55”得到当天 15:55。指定“今天”时只能在今天选择，均已过则手动补全。 |
| 17:20、17：20 | 默认 24 小时制；没有日期时取最近未来的一次该钟点，今天已过则明天，并提示确认。冒号表达带时段时尊重时段。 |
| 今天下午 3 点、下午三点、晚上八点 | 明确时段优先；无日期时取下一次该时段钟点。明确指定今天且已过则要求补全，不能静默改成明天。 |
| 明天、后天、明早、后天上午 | 相对当前自然日计算；只有日期/时段而无小时，日期可预填，时间保持缺失。 |
| 周五晚上、本周六、下周一 | 按以周一为首的本地周计算；“本周”已过的目标日需提示并要求选择，不能默认为下周。 |
| 9 月 20 日、下个月 1 号 | 取最近未来的对应日期；若当年该日期已过，可建议下一年并显示警告，必须由用户确认。 |
| 五分钟后、过五分钟、两小时后、半小时后、1.5小时后、一小时三十分钟后 | 完整提取并累加时长，基于 `currentTime` 加时，向上取整到分钟；不得截取小数尾部。三天后无钟点按当前时刻加三天，有钟点则作为日期偏移。零/负时长、非整数分钟和超过一年时长要求补全。 |

通用规则：只有日期时必须补时间；未指定日期/时段时采用最近未来的合理候选，推断时提示用户确认；明确日期优先，明确已过时间返回空时间与手动确认提示，不生成过期草稿。过去时间禁止保存，确认页给出日期时间选择；时间以 `Asia/Shanghai` 计算，保存时服务端复核。当前实现为 `rule-fallback-v3` 规则解析，尚未接入 AI 模型，不承诺任意自然语言理解。完整能力、歧义兜底和验收边界见 [时间解析规则](./TIME-PARSING-RULES.md)。

### 12.4 标题、地点、备注

标题取可执行的核心动作/事件，删除时间词、语气词和“提醒我”，例如“明天下午三点去拿快递”→“去拿快递”。地点仅提取明确场所、地址或线上会议标识，不确定则留空。附加要求、携带物、联系人补充说明进入备注，例如“记得带合同”→备注；标题宁短不丢失核心事项。

### 12.5 解析失败兜底

AI 超时、格式不合法、字段无效或置信度低时：返回 `parseWarnings`，跳转预填原始文本的手动确认页；日期时间为空、标题可将原文截断预填。展示“请补全后保存”，提供“重新解析”，禁止静默丢弃输入或直接保存。

## 13. 数据结构设计

集合名：`reminders`。所有时间以数据库 `Date`（UTC 存储）保存，客户端按 `Asia/Shanghai` 展示。

| 字段 | 类型 | 必填/默认 | 说明 |
| --- | --- | --- | --- |
| `_id` | string | 是，数据库生成 | 记录 ID |
| `openid` | string | 是 | 所有权标识，不向客户端信任传入 |
| `title` | string | 是 | 1–60 字 |
| `remindAt` | Date | 是 | 事项发生/提醒基准时间 |
| `remindOffsetMinutes` | number | 是，0 | 0–525600 分钟；常用值提供快捷选项，也支持自定义 |
| `notifyAt` | Date | 是 | `remindAt - offset`，便于索引扫描 |
| `location` | string | 否 | 最多 100 字 |
| `note` | string | 否 | 最多 300 字 |
| `status` | enum | 是，`pending` | `pending/completed/deleted` |
| `sourceType` | enum | 是 | `text/clipboard/voice/image`；V1 写 text/clipboard |
| `sourceText` | string | 否 | 原文，建议默认不长期保存；见第 17 节 |
| `aiConfidence` | number | 否 | 0–1，仅分析使用 |
| `parseResult` | object | 否 | 受控字段：原始 AI 输出、警告、模型版本；不保存敏感推理文本 |
| `notifyStatus` | enum | 是，`pending` | `pending/authorized/denied/sent/failed` |
| `notifyAttemptCount` | number | 是，0 | 最多 3 次，防重复轰炸 |
| `completedAt` | Date | 否 | 完成时间 |
| `deletedAt` | Date | 否 | 软删除时间 |
| `createdAt` / `updatedAt` | Date | 是 | 服务端生成/更新 |

索引建议：`{openid:1,status:1,remindAt:1}` 支持列表；`{status:1,notifyStatus:1,notifyAt:1}` 支持定时发送；`{deletedAt:1}` 支持清理。若 CloudBase 索引限制不同，以实际控制台配置为准。

## 14. 云函数/接口需求

所有云函数从运行上下文取得 openid，不接受客户端声明的 openid；统一返回 `{code, message, data, requestId}`，业务错误不泄露模型密钥或内部堆栈。

| 云函数 | 入参 | 出参与核心逻辑 | 权限/异常 |
| --- | --- | --- | --- |
| `parseReminder` | `text,currentTime,timezone,locale,sourceType` | 返回第 12 节解析结果；长度/频率校验→调用 AI→JSON 校验与时间复核 | 要求登录态；超时/模型错误返回可手动填写错误码；限流防滥用 |
| `createReminder` | 草稿字段、订阅授权结果 | 返回 `reminderId`；二次校验→写入 owned reminder→记录通知状态 | openid 从上下文取；过去时间、越权字段、DB 失败均拒绝 |
| `getReminders` | `group`、`cursor`、`pageSize` | 返回当前用户的分组列表与分页游标 | 过滤 deleted；pageSize 1–50；DB 失败可重试 |
| `updateReminder` | `id`、允许编辑字段、授权结果 | 返回更新记录；重新计算 `notifyAt`、重置通知状态规则 | 查询条件必须含 `_id+openid`；不存在返回 404 |
| `deleteReminder` | `id` | 返回成功；软删除、写 `deletedAt` | 仅本人；幂等删除返回成功 |
| `completeReminder` | `id` | 返回完成时间；仅 `pending` 可转 completed | 仅本人；重复调用返回当前状态 |
| `sendReminder` | `runToken`（定时器内部） | 扫描到期记录、逐条发送、记录 sent/failed 和次数 | 仅定时触发身份可调用；单条幂等锁/条件更新；平台错误分类记录 |

`sendReminder` 应采用“条件更新抢占”处理并发：发送前以 `pending + authorized + notifyAt<=now + 未发送锁` 原子标记 `sending`（可作为内部临时状态，不对前台暴露），成功写 `sent`，失败写 `failed` 或按可重试错误回退。**待确认：** 微信订阅消息是否允许按该扫描策略发送，须按当前官方能力落地。

## 15. 状态流转

### 2026-10-15 页面流程补充

首页仍区分待提醒预览和提醒记录列表；详情不分册，统一包含当前用户全部未删除事项，按创建时间正序翻页，最新创建在最后。所有入口按 ID 定位，已发送页不因状态变动而消失。旧 scope 参数仅兼容接收、不再用于筛选。保存成功后返回首页清空已提交的原句及旧提示；取消、失败不清空，其他新草稿不被旧请求误删。

### 2026-10-14 产品决策（覆盖下文旧版完成流程）

Ping 是到点提醒工具，不再要求用户手动完成事项。新客户端移除 `completeReminder` 操作入口，但保留旧接口和历史 `completed` 数据以兼容已安装的旧版本，不批量修改数据。

- 首页待提醒范围：未删除、非旧手动完成且通知状态不是 `sent`；授权拒绝、失败、错过与不确定仍可见，不能由时间到点自动认定成功。
- 提醒记录范围：未删除且 `notifyStatus=sent` 或旧 `status=completed`。各记录分别显示 `已提醒`、`历史已完成`；不互相转换。
- 新成功记录的业务 `status` 仍为 `pending`；`notifyStatus=sent` 驱动自动归档，用户没有额外操作。通知微信接受不代表已读，更不代表事情办完。
- 我的统计使用真实 `remindedCount`；保留 `completedCount` 供旧客户端使用。
- 更新现有未来时间的已提醒记录后，重置通知状态使其重新进入待提醒；旧手动完成记录仍仅保留查看和删除，不消费新授权。
- 返回首页/详情及下拉刷新重新查询云端；不是根据本地钟表推测发送结果。

以下状态图为旧版兼容说明，不再作为新客户端的操作流程。

```text
提醒：pending --用户完成--> completed
       pending --用户删除--> deleted
       completed --用户删除--> deleted

通知：pending --用户授权--> authorized --发送成功--> sent
       pending --用户拒绝--> denied
       authorized --平台/网络失败--> failed
       failed --可重试且未超次数--> authorized
```

`pending` 表示提醒已保存但未得到可发送授权；`authorized` 表示当前条目具备待发送资格；`denied` 不尝试发送；`sent` 是发送接口成功返回而非“用户已阅读”；`failed` 是最终失败或次数耗尽。删除/完成均使 `sendReminder` 停止处理该提醒。

## 16. 异常与边界情况

| 情况 | 产品表现 | 技术处理 |
| --- | --- | --- |
| 输入为空/超长 | 按钮不可点/提示最多 500 字 | 前后端长度校验 |
| AI 解析失败、超时、格式错误 | 保留原文，给重试与手动填写 | 超时 8 秒；解析 JSON schema 校验；记录错误码 |
| 无法识别时间/时间已过 | 缺字段/过去时间提示，禁止保存 | 确认页必填校验与服务端时间复核 |
| 授权拒绝 | 仍可保存，说明不保证通知 | 写 `denied`，下次主动保存时再请求 |
| 通知发送失败 | 详情/列表可见“通知未发送” | 记录平台错误、幂等重试至多 3 次 |
| 网络或数据库失败 | 不清草稿，提供重试 | 统一错误码、请求幂等键（创建） |
| 删除即将提醒事项 | 立刻从列表移除 | 条件更新为 deleted；扫描时再次校验状态 |
| 修改提醒时间 | 立即更新分组与通知资格 | 重新计算 notifyAt，清除旧发送锁 |
| 剪贴板为空/过长/非提醒 | 不弹卡/提示可手动创建 | 仅本地判断，未经确认不上传 |
| openid 获取失败 | 提示“暂无法保存，请稍后重试” | 云函数鉴权失败；不可写入匿名数据 |
| 重复点击保存 | 只创建一条 | 客户端禁用 + `clientRequestId` 幂等去重 |
| 同名同时间提醒 | 允许 | 不做去重，避免误删真实需求 |

## 17. 权限与隐私要求

遵循最小化收集：仅收集完成提醒所需的 openid、用户主动提交的文本/字段、提醒时间和必要操作日志。剪贴板必须先展示本地确认卡，用户点击“使用此内容”后才上传 AI；不得自动上传、不得读取剪贴板历史。

建议 `sourceText` 默认不保存；为排查解析问题可在用户明确同意“帮助改进解析”时保存，且最长保留 30 天并脱敏。若必须默认保存，应在确认页和隐私政策中明确用途、保存期与删除方式。AI 解析使用第三方模型时，在隐私政策说明数据类别、服务商、处理目的、传输安全与不用于训练的约定（以供应商条款为准）。

隐私政策须说明订阅消息授权用途、云端数据存储、日志、反馈渠道、用户查询/删除方式、第三方 SDK/AI。用户删除单条提醒后立即前台不可见；用户注销或删除请求应删除/匿名化其提醒和原文，最迟在 30 天内完成（具体法务要求**待确认**）。

## 22. 后续版本规划建议

仅当 V1 验证了二次使用、解析质量和通知价值后，按用户反馈优先级评估：语音输入、截图 OCR、重复提醒、微信聊天转发能力探索、日历同步、模板提醒与轻量商业化。每项先验证是否缩短“怕忘 → 已设提醒”的路径；不因功能完整度而扩展为任务管理或知识产品。
