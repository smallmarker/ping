# 资源点消耗整改（2026-11-06）

## 证据与范围

用户控制台截图：当前套餐周期 2026-10-09 至 2026-11-08，总消耗 3123.55 点。数据库 1314 点（6.57 万次），环境调用 1216.76 点（云开发 API 5.53 万次、小程序 API 3.32 万次），云函数 296.44 点（3.96 万次、2182 GBs），日志 296.35 点。各类次数不可直接相加视为用户访问量；同一业务流程可能触发多项计量。

本地代码证实 `sendReminder` 每分钟执行，原来空轮次通常有两次数据库查询并输出一次结果日志。3.96 万次函数调用与约 27.5 天的每分钟定时任务吻合，但控制台未连接成功，不能声称已核实全部线上调用来源、重复触发器或日志计量单位。

## 第一轮：调度与日志（本地，未部署）

- 原定时器 `pingReminderEveryMinute`、每分钟 cron、微信来源校验、每轮最多发送一条、2200ms 软预算和 3 秒平台限制均不变。
- 到点提醒仍每分钟查询，不增加“空列表”缓存，不依赖是否有用户在线。
- 仅无到点提醒时，按绝对分钟 `% 5 === 0` 查询一个异常记录。冷启动不会重置节流，维护不占用有到点提醒的轮次。
- 原子领取、版本校验、防止删除后发送、限流重试、结果未知不自动重发均保持；不调整业务记录结构，不批量删除数据。
- 空轮次应用日志按整点采样。实际发送、维护、竞争跳过、预算不足和数据库/发送异常仍记录，不记录提醒正文、OpenID 或模板内容。
- 保留函数返回的完整计数，减少的是应用主动写出的空轮次日志，不关闭错误日志、平台运行日志或整个日志服务。
- 保留首页/详情返回刷新的语义，避免重现此前已修复的数据不同步；第二轮仅合并重复读取。源代码未发现前端 `setInterval` 或数据库实时监听，尚不能解释截图中的全部小程序 API 调用。

## 预期收益与边界

在连续空闲、无延迟/重试、单触发器、每分钟一轮的假设下：

| 24 小时 | 整改前 | 整改后 |
| --- | ---: | ---: |
| 定时函数调用 | 1440 | 1440 |
| 数据库查询 | 2880 | 1728 |
| 主动空轮次结果日志 | 1440 | 24 |

空闲数据库查询减少 40%；空轮次应用日志条数减少约 98.3%。不承诺环境调用或日志总账单按同样比例下降；平台 START/END/REPORT、自动采集日志及保留期仍可能计费。五分钟维护槽不保证服务停机、调度延迟或持续有到点任务时的固定完成时限。

正常到点发送不降低检查频率。代价是过期标记、发送中租约恢复等异常状态通常延后至后续五分钟空闲维护槽，每槽最多处理一条。旧版 `claimed` 租约若恢复时已超过五分钟发送窗口，将如实标为错过，不能为省钱或补发而发送过期消息。结果未知仍不重发，避免重复通知。

## 验证

新增 `tests/reminder-idle-cost.test.js`：模拟一整天 1440 次冷启动（1728 次查询、24 条健康日志）；普通分钟新建提醒立即在下一轮被发现；到点发送优先于维护；延后维护、慢查询预算、数据库错误日志、过期旧领取及已删除记录防重发。既有维护测试改为显式五分钟时钟，不依赖测试运行时刻。

## 部署与线上核对（待执行，不自动上传）

1. 保存云端当前 `sendReminder` 代码/配置备份，核对环境、模板环境变量、Node 运行时、3 秒超时及原触发器。
2. 第一轮可独立仅部署 `sendReminder`，保留原 cron 和环境变量；不要新建第二个触发器，不上传前端、不改变线上版本。第二轮的生效条件见下文。
3. 真机创建一条未来几分钟提醒，确认通知送达、只送一次、数据库状态已更新。
4. 观察至少一个自然日：空闲轮次约一次查询，五分钟维护轮次最多两次。实际成功发送/错误仍能在日志中查到，整点有空闲健康记录。
5. 控制台核查云函数调用按函数分布与触发器清单，确认没有重复触发；检查环境调用分日曲线及归因信息。不能将“小程序 API”全部断言为定时器调用。
6. 日志页面核实“4.7 GB”的统计口径、对应日志主题和保留期限。若需要缩短保留期，先告知历史排查记录将丢失并取得用户确认；不直接清空日志或关闭告警。
7. 若仍超套餐，单独验证按需/延迟调度能力、费用、免费版资格与可靠恢复，再决定替换每分钟轮询；不得只拉长发送 cron（会延误通知），也不得依赖热实例内存缓存下一次时间（冷启动/新增提醒会失效）。

部署前本地修改不会降低已上线环境的资源消耗；已产生的用量不会因代码整改退回。

## 第二轮：读取去重与统计（本地，未上传或部署）

### 已实现

- 服务层按“读取类型 + 排序/ID + 本机成功写入版本”合并进行中的请求，列表和单条记录只复用进行中的 Promise，不跨已完成读取设置 TTL。
- 创建、修改、删除和旧版完成写入成功后使用新的读取版本，不能复用写入前的旧请求；写入失败不假装更新。原有本地写入覆盖、分页完整性和旧响应防覆盖机制保留。
- 失败请求从进行中映射移除，允许重试。强制读取选项可绕过去重，用于明确要求新快照的场景；测试保留并覆盖不同版本/不同排序的读取竞争。
- 详情编辑入口不再订阅 `updated` 后提前加载；编辑返回由原有 `onShow` 刷新一次。通知入口先按 ID 读取、整册加载失败仍可查看单条的行为不变。
- “我的”统计使用 30 秒内存缓存（自成功读取算起）；重复并发请求合并。创建/修改/删除/旧完成成功立即失效；强制重试绕过缓存，过期后访问重新读取，未引入后台定时刷新。
- 统计的短缓存不是实时通知计数；其他设备或后台通知带来的变化，可能在 30 秒缓存期后、用户再次进入页面时显示。用户本机写入不能使用该缓存拖延同步。
- 写入前启动的统计返回时若版本已变，转为读取/复用新版本结果；同版本旧强制请求不得覆盖已确认的新数字。页面还有请求版本校验，旧请求不能清除新请求的错误提示。
- 新客户端统计传 `includeLegacyCompleted: false`，云端只执行两次 count，省去不展示的旧已完成统计；未传此参数的旧客户端仍得到原来三个统计。前后端任一先部署均保持兼容，但减少 count 需新版云函数和新版客户端同时使用。
- JS 与 TS 源码同步，未修改任何 WXML/WXSS，不新增 UI、授权或付费功能。

### 本地测得的收益

| 场景 | 整改前 | 整改后 |
| --- | ---: | ---: |
| 121 条记录，两个相同并发列表加载 | 6 次云函数调用 | 3 次 |
| 121 条记录，编辑回调已完成后再返回详情 | 8 次读取调用 | 4 次 |
| 新客户端一次统计请求 | 3 次 count | 2 次 |
| 30 秒内无本机写入、无强制重试的重复统计访问 | 每次都调用云端 | 复用首次成功结果 |

这是场景级调用减少，不代表总账单等比例减少。单人低频使用时，全天轮询仍是主要问题。

新增 `tests/resource-read-optimization.test.js` 共 12 项：跨页并发去重、失败后重试、不同排序/强制读取隔离、成功写入后的读取版本、删除不复活、单条查询去重、统计 TTL、失败写入不误失效、成功写入立即失效、统计旧响应防覆盖、旧客户端兼容、详情返回刷新和我的页重试错误保护。

### 生效步骤与尚未做的优化

- 第二轮需要部署 `getReminders`，并在用户明确要求上传后发布新版小程序；未部署、未上传期间线上保持原逻辑。旧版本继续正常统计。
- 首页摘要与历史分页、按需书页加载仍未重构；目前一个完整列表仍会拉全部未删除记录。该改动需要同时保持准确分组数量、首页 3 条、查看更多定位及统一书册翻页，不能仅截断分页或把缓存当成完整数据。
- 纯规则解析下沉本地、建集合改为环境初始化也未改动，避免混入解析分叉、新环境首次写入失败等风险；服务端的字段校验、幂等及归属检查均保留。

## 按需调度核查结论：未切换线上方案

官方 [CloudBase 触发器文档](https://docs.cloudbase.net/cli-v1/functions/configs) 说明支持 timer 与七段 cron，并提示每个函数一个触发器；[SCF 说明](https://cloud.tencent.cn/document/product/583/9708) 支持指定年月日时分秒，但 SCF 的管理能力不能直接视为当前微信云开发环境的权限和事件来源保证。

尚未验证当前环境能否通过服务端安全地创建/更新一次性计划、管理 API 所需授权、免费套餐限制、配额和任务恢复；现有发送函数严格要求 `SOURCE=wx_trigger` 和既有触发器名，不能为接入其他调度通道而直接放宽该校验。不能以任意客户端传来的时间/用户标识作为调度授权，也不能把凭据塞进小程序。

可验证的候选设计为“持久化最近待发送时间 + 安全更新下一次唤醒 + 低频兜底”。上线前必须覆盖并发更早新增、修改/删除、跨日期时区、计划创建失败但记录已保存、发送成功回写失败、触发器重复/丢失、调度重新启动和 3 秒预算。未经实环境验证，不替换当前每分钟调度，不承诺节省幅度。
